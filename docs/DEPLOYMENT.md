## 1. One release, one document root (since 2026-10-30)

| What moves | Mechanism | Trigger |

On 2026-10-30 a dry run showed the live server equal to `main` (545 tests passed). The FTP workflow and `scripts/deploy-ftps.sh` were replaced; the owner deletes the FTP secrets and account.

Because PHP now ships on every push, **a PHP change that needs a schema change must not reach `main` before its SQL has run on the live database** (or must tolerate the old schema).

**A PHP change under `server/` goes live on the next push to `main`; a schema change does not.** SQL is applied
by a person, and `server/.htaccess` is uploaded by hand. This is the single most common way work here looks finished and is not.

## 2. The deploy workflow

The deploy key is restricted (`restrict`, label `github-deploy-gakinz_com` in the server's

### What `dist/` holds (prerendered since 2026-10-16)

`npm run build` prerenders the public site (`docs/ARCHITECTURE.md` section 2, "Build-time
prerender"), so `dist/` now holds, besides `assets/` and the files from `public/`:

| File | Served for |
|---|---|
| `index.html` | `/`, prerendered |
| `<path>/index.html`, e.g. `work/index.html`, `work/rotaflow/index.html` | each prerendered public page, 30 on 2026-10-16 |
| `app-shell.html` | everything else: `/app/*`, `/login`, `/set-password`, `/p/:token`, `/verify/:id`, a CMS-only record, unknown paths |
| `sitemap.xml` | `/sitemap.xml`. Generated by the build from the prerendered pages since 2026-10-16 (K-019); `public/sitemap.xml` was removed |

The build makes no network request and needs no browser, so it runs unchanged in CI and in
the deploy workflow. `dist-ssr/` is a build intermediate, deleted by the build, and never
shipped.

**A prerendered page shows the built-in content, not the CMS.** Projects, services, site copy
and posts in the HTML come from `src/marketing/data/`. In the browser, the CMS answer replaces
them once the bundle has loaded, exactly as before. A crawler that does not run JavaScript
sees only the built-in version, so **a CMS change reaches the HTML only on the next deploy**:
push any commit to `main`, or re-run the deploy workflow, after publishing something that
crawlers should see. A record that exists only in the CMS has no prerendered page; it is
served `app-shell.html` and renders in the browser.

`server/.htaccess` routes these files (section 5.3). It is uploaded by hand, like every server
file, and does not ship in `dist/`. Either order is safe: with the old `.htaccess`, `/work` is
redirected to `/work/` and served its page, and an unknown path is sent the prerendered home
page, which the client replaces with the right page; the new `.htaccess` falls back to
`index.html` until `app-shell.html` exists.

Everyday loop:

```bash
git add . && git commit -m "..." && git push
```

Then watch the repository's Actions tab. The deploy starts only after the CI workflow passes
on that push; a red CI run means nothing is deployed.

### Before you push

```bash
npm run build          # runs tsc -b first, so a type error blocks the deploy
npm test               # unit tests (src/)
npm run test:server    # PHP endpoints against a throwaway local *_test database
npm run lint:ratchet   # fails if the lint backlog (K-002) grows
npm run docs:check     # links, and the document-sync rule in AGENTS.md
npm run check:live     # after a release: read-only GETs against the live site (section 5 list)
```

CI runs all five, plus `php -l` over `server/`, and the deploy waits for it.

### Release policy

Approved 2026-10-10. Until then CI ran no tests and the deploy did not wait for it (K-035).

- **Keep the Vite build and the existing client and server model.** CI runs unit tests, the
  server tests and PHP syntax, and gains targeted synthetic endpoint and browser checks as
  they become available.
- **Lint is a ratchet first, then a gate.** `npm run lint:ratchet` enforces the ceiling
  in `scripts/lint-ratchet.mjs`; the current figure is in `docs/STATUS.md` (K-002). Clear the errors in small batches, then make
  lint blocking. `continue-on-error` alone is advisory, not a ratchet.
- **Production deploys only after the required checks pass**, or through a deliberate,
  approved release trigger. Every push to `main` with code changes releases `dist/` and
  `server/*.php`; documentation-only pushes do not (`paths-ignore` in `deploy.yml`).
- **SQL, `.htaccess` and `config.php` stay deliberate operator actions**, recorded in section 5
  with their evidence and rollback.
- **Small reviewed batches**, one concern each, on feature branches. Never `npm audit fix
  --force`, a framework change, or every improvement merged into one unreviewable release.
- **Dependencies.** Identify reachable advisories, update compatible versions in small
  batches, and remove unnecessary exports only with approval (K-041). A CSV-only export may
  remove the `xlsx` problem if nobody needs workbooks (K-017). A Tailwind major migration is
  never an automatic audit fix. Any lockfile update needs a fresh build and test run.

## 3. Server deploy

The server has no Node, so nothing is built there. PHP files go up as source with each release
(section 1), after `php -l` passes on every file; nobody uploads PHP by hand.

Settings: the real values live in `~/private-config/gakinz_com/config.php` (mode 600, outside every
web root, since 2026-10-30). The document root holds a `config.php` stub with no secrets that loads
it; its text is `server/config.stub.php.example` (added 2026-11-01, so it can be reviewed). A release never uploads a file named `config.php`, so neither is overwritten, and neither leaves
the server. Add or change a key with `scripts/set-server-key.sh` (it prompts with hidden input and
writes over SSH) or by a person on the server; never through the repository.

## 4. First-time server setup

Adapted from `server/README.md`, which has been corrected as part of this migration.

1. Upload the contents of `server/` to the document root, except `config.php.example` and
   `README.md`.
2. Copy `config.php.example` to `config.php` on the server and fill in the real values.
3. Run `schema.sql` against the project database through phpMyAdmin.
4. Create `server/uploads/` in the document root and make it writable. `files.php` creates it
   and drops a deny-all `.htaccess` on first use, but a pre-created directory avoids a
   permissions surprise.
5. Confirm `GET /api.php` returns `{ ok, php, db }` (D-031).

There is no `/smoke` route any more. The public smoke-test page and its route were removed
during the demo-surface cleanup, so step 5 of the old instructions could not pass.

#### Before switching on reference sign-in

Every one of these must hold before `$REFERENCE_SIGNIN_ENABLED = true` goes into the live
`config.php`. None holds today.

1. **Timing.** The host's PHP provides early finish (`fastcgi_finish_request` on PHP-FPM, or
   `litespeed_finish_request` on LiteSpeed), or the SMTP send is capped below the 1000 ms floor
   (a shorter SMTP timeout or a local relay). Otherwise a match is measurably slower than a
   miss when SMTP is slow (`docs/KNOWN-ISSUES.md` K-101).
2. **Separate link purposes.** A `purpose` column on `magic_links`, added when the auth upload
   set (`_bootstrap.php`, `auth.php`, `oauth.php`, `users.php`) is next opened, so
   `magic_consume` accepts only magic-link rows and `client_access.php` only its own. That
   closes the window of up to 15 minutes in which a reference link still works through
   `magic_consume` after the switch goes off (K-100). It will be a future SQL number.
3. **Real client IP.** `REMOTE_ADDR` is the visitor's address behind Cloudflare (mod_remoteip
   or an equivalent). Otherwise every per-IP throttle counts Cloudflare's edge addresses and can
   block many people at once (K-102).
4. **Owner policy.** The owner confirms the client sign-in policy (`docs/PRODUCT-SPEC.md`
   section 6.1: "The final owner and client sign-in policy is confirmed before that work
   starts"), recorded in `docs/STATUS.md` section 5.

Then switch it on, and walk the J02 and J03 rows of `docs/TEST-PLAN.md` on the live host with a
client account the owner agrees to use. Switching it off again is the same key set back to
`false`.

## 6. Rollback

| Track | Rollback |
|---|---|
| Client | Revert the commit and push. Actions rebuilds and re-uploads |
| Server | Re-upload the previous version of the file. Keep a copy before overwriting |
| Schema | There is no down migration. A column addition is additive and safe to leave; an `UPDATE` such as the timesheet grandfathering is not reversible |

## 7. Troubleshooting

| Symptom | Likely cause |
|---|---|
| Actions run fails at `npm ci` | `package-lock.json` out of step with `package.json` |
| Actions run fails at `npm run build` | A TypeScript error. `tsc -b` runs first |
| Actions run fails at the FTP step | One of the three secrets is wrong or the host changed |
| API returns "Database connection failed" | Wrong credentials in the server `config.php`, or the user lacks privileges |
| API returns a 500 on a feature that works locally | A migration has not been run |
| A feature returns 503 | Its configuration key is not set on the server |
| Actions run fails at `prerender:` | A listed public path rendered the 404 page or lost its title or canonical, or `index.html` lost its `seo:start` and `seo:end` markers. The message names the path |
| A public page shows old projects or copy with JavaScript off | The prerendered HTML is from the last build. Redeploy after publishing (section 2) |
| `/app` or `/login` shows the home page for a moment | The old `.htaccess` is live and sends `index.html`; upload the new one |
| Browser reports a CORS failure in development | The dev port drifted from 5102, or the live `ALLOWED_ORIGINS` does not list it |
| An endpoint 404s | The PHP file was never uploaded |

DNS, TLS certificates, mail hosting and Cloudflare proxy state are **out of scope for this
repository**. Earlier revisions of the project documentation gave instructions in those areas
that were wrong and caused outages. Read the operator's global notes instead.
